# Laser Arena --- Game Specification 

## 1. Project Goal

Build an open, browser-based multiplayer game called **Chapball**.

The game is a real-time multiplayer strategy game where each player
controls a small player/laser object on a 2D arena.

Each player:

-   Has a colored player marker.
-   Has a laser beam pointing in one direction.
-   Can secretly choose their position and laser direction.
-   **Cannot see the other players' positions or laser directions while
    players are preparing.**
-   When everyone is ready, the game reveals all players and laser beams
    at the same time.
-   A laser that hits another player's marker eliminates that player.
-   Eliminated players are removed from future rounds.
-   After each round, the playable arena shrinks.
-   The game continues until a winner is determined.

The game should feel minimal, clean, fast, competitive, and easy to
understand.

------------------------------------------------------------------------

# 2. Technology Requirements

Use:

-   **Next.js** with SSR
-   **Node.js**
-   **Express**
-   **Socket.IO** or an equivalent WebSocket solution for real-time
    multiplayer
-   HTML Canvas or SVG for the game arena
-   JavaScript/TypeScript

### Important architecture requirement

Use **ONE server only**.

Do NOT create a separate Next.js server and separate Express server.

The architecture should be:

``` text
Browser
   |
   v
Node.js + Express
   |
   +---- Next.js SSR
   |
   +---- Socket.IO
   |
   +---- In-memory game rooms
```

Next.js should be rendered through the same Node/Express server.

There is **no database**.

There are **no user accounts**.

There is **no login system**.

There is **no registration system**.

All game data exists only in server memory.

If the server restarts, all active rooms and games can disappear.

This is intentional.

------------------------------------------------------------------------

# 3. No Database / No Accounts

The game must be completely open.

A player should be able to:

1.  Open the website.
2.  Enter a display name.
3.  Create a room or join a room.
4.  Start playing.

Do not require:

-   Email
-   Password
-   Account creation
-   Authentication
-   Database records
-   Profiles

Each player receives a temporary unique player ID generated by the
server.

Example:

``` js
playerId = "p_8f31a2"
```

The player name is only stored in the active room.

# 4. Game Modes

There are two room modes:

## Public Room

A public room can be joined through the public room interface.

Players can discover/join an available room according to the
implementation.

## Private Room

A private room is accessed using a room code or shareable room link.

Example:

``` text

```

or:

``` text
/game/AB7K9
```

Private rooms should not be publicly discoverable.

# 7. Player Object

A player should have data similar to:

``` ts
type Player = {
  id: string
  name: string

  team: "A" | "B" | null

  x: number
  y: number

  laserAngle: number

  ready: boolean
  eliminated: boolean
  connected: boolean
}
```

Coordinates should preferably be normalized:

``` text
x = 0.0 → 1.0
y = 0.0 → 1.0
```

This makes the game responsive on different screen sizes.

------------------------------------------------------------------------

# 8. Hidden Placement Phase

This is one of the most important mechanics.

When a round starts, each player gets a private placement screen.

The player can see:

-   Their own marker
-   Their own laser
-   The current arena boundaries
-   Their own controls
-   Countdown
-   Ready button

The player CANNOT see:

-   Other players
-   Other players' positions
-   Other players' laser directions

The server must enforce this.

Do not simply hide other players with CSS while sending their data to
the browser.

The server should only send each client the information that client is
allowed to know.

------------------------------------------------------------------------

# 9. Player Placement

The player can place their marker anywhere inside the current arena.

The player should be able to:

-   Drag their player marker.
-   Choose/rotate their laser direction.
-   See the laser extending from their marker.
-   Confirm their placement.

The laser should visually extend from the player's marker until it
reaches the arena boundary.

Example:

``` text
      laser
        /
       /
      ●
   player
```

The player should not be able to place the marker outside the arena.

------------------------------------------------------------------------

# 10. Laser

Each player has exactly one laser.

The laser is represented by:

``` ts
{
  x: number
  y: number
  angle: number
}
```

The laser should extend infinitely until it reaches the arena boundary.

The visible laser line should be clipped to the current arena.

Example:

``` text
●────────────────────────>
```

or:

``` text
       /
      /
     /
    ●
```

------------------------------------------------------------------------

# 11. Ready System

Every active player must press:

``` text
READY
```

Once ready, their placement becomes locked.

The player can no longer move their marker or rotate their laser.

The server tracks:

``` text
readyPlayers
totalPlayers
```

Example:

``` text
6 / 8 Ready
```

When every active player is ready:

``` text
REVEAL
```

begins automatically.

------------------------------------------------------------------------

# 12. Countdown

The preparation phase has a countdown.

Example:

``` text
60
59
58
...
3
2
1
```

If all players become ready early, do not wait for the entire countdown.

Start the reveal immediately.

If the countdown reaches zero, automatically lock any players who have
not submitted a valid placement and handle them according to the game's
defined fallback behavior.

Recommended fallback:

-   Keep their latest valid position.
-   Keep their latest valid laser direction.
-   Automatically mark them ready.

The server must be authoritative for the countdown.

------------------------------------------------------------------------

# 13. Reveal Phase

When everyone is ready:

1.  Freeze all placements.
2.  Reveal every active player's position.
3.  Reveal every active player's laser.
4.  Calculate all laser/player collisions.
5.  Determine eliminations.
6.  Show the result.

The reveal should feel dramatic.

Suggested sequence:

``` text
PLACEMENT
    ↓
EVERYONE READY
    ↓
SHORT REVEAL ANIMATION
    ↓
LASERS APPEAR
    ↓
HIT DETECTION
    ↓
ELIMINATIONS
```

------------------------------------------------------------------------

# 14. Collision / Hit Detection

The server must calculate laser collisions.

Do NOT trust the browser to determine who was hit.

A laser is a ray starting from:

``` text
(x, y)
```

and traveling in:

``` text
angle
```

The server should determine whether that ray intersects another player's
marker.

Use proper geometry/math rather than checking whether two rendered lines
visually overlap.

The player marker should have a configurable hit radius.

For example:

``` text
laser → ray
player → circle
```

If the distance from the player's center to the laser ray is less than
the player's hit radius AND the player is in front of the laser origin,
the player is hit.

------------------------------------------------------------------------

# 15. Multiple Hits

A single laser can potentially hit more than one player.

The game should support this.

Example:

``` text
Player A
    |
    | laser
    |
    ● Player B
    |
    ● Player C
```

Both B and C can be hit if the laser passes through both.

The server should determine all valid hits.

------------------------------------------------------------------------

# 16. Self-Hit

A player should NOT be able to eliminate themselves with their own
laser.

Ignore the laser's intersection with its own origin/player marker.

------------------------------------------------------------------------

# 17. Same-Time Elimination

All laser calculations for a reveal should be based on the positions
that were locked at the beginning of the reveal.

Do not eliminate a player and then recalculate the other lasers using
the changed state.

In other words:

``` text
Round state
    ↓
Calculate ALL hits
    ↓
Collect ALL eliminated players
    ↓
Apply eliminations simultaneously
```

This prevents inconsistent results.

------------------------------------------------------------------------

# 18. Team Mode

If team mode is enabled, there are exactly two teams:

``` text
TEAM A
TEAM B
```

A team should not be eliminated simply because one player was hit.

Instead, individual players are eliminated.

The team remains active while it still has at least one active player.

The game should support a team victory condition.

Recommended team victory:

``` text
Team A wins when Team B has zero active players.

Team B wins when Team A has zero active players.
```

If the game is not in team mode:

``` text
Last remaining player wins.
```

------------------------------------------------------------------------

# 19. Friendly Fire

Make friendly fire a configurable game rule in the code architecture.

Initial recommended behavior:

### Team Mode

Friendly fire OFF.

A Team A laser cannot eliminate another Team A player.

A Team A laser can eliminate Team B.

### No-Team Mode

Every player can hit every other player.

Keep this logic isolated so it can be changed later.

------------------------------------------------------------------------

# 20. Arena Shrinking

This is a major feature.

After each round, the playable arena becomes smaller.

The screenshots provided show the intended visual idea:

``` text
Round 1

+--------------------------------+
|                                |
|          ●                     |
|                                |
|    ●                     ●     |
|                                |
+--------------------------------+


Round 2

      +----------------------+
      |                      |
      |   ●            ●     |
      |                      |
      |       ●              |
      +----------------------+


Round 3

          +--------------+
          |              |
          |  ●       ●   |
          |              |
          +--------------+
```

The arena should visually shrink toward its center.

Do not simply resize the browser element.

The **game world's playable coordinate system** should shrink.

The server should store an arena state such as:

``` ts
type Arena = {
  x: number
  y: number
  width: number
  height: number
}
```

or:

``` ts
type Arena = {
  scale: number
  centerX: number
  centerY: number
}
```

------------------------------------------------------------------------

# 21. Arena Shrink Animation

The arena should not instantly become smaller.

After the round result:

``` text
ROUND RESULT
     ↓
ELIMINATED PLAYERS DISAPPEAR
     ↓
ARENA SHRINKS
     ↓
NEXT ROUND
```

Use a smooth animation.

Suggested duration:

``` text
1–2 seconds
```

The shrinking should be synchronized for every connected client.

The server decides the new arena size.

Clients animate toward the server-provided target.

------------------------------------------------------------------------

# 22. Shrink Amount

The exact shrink formula should be centralized in one function.

Example concept:

``` ts
function getArenaScale(activePlayers: number) {
  // return scale based on remaining players
}
```

Do not hardcode the arena size in multiple components.

The game should make it easy to tune the shrink curve later.

Example:

``` text
8 players → 1.00
7 players → 0.92
6 players → 0.84
5 players → 0.76
4 players → 0.68
3 players → 0.58
2 players → 0.48
```

These are starting values only.

------------------------------------------------------------------------

# 23. What Happens to Player Positions After Shrinking?

The important rule is:

**Do not randomly move surviving players.**

When the arena shrinks, existing player positions should be transformed
into the new arena coordinate space.

If a player's position would fall outside the new playable area, clamp
it to the nearest valid position.

The laser angle should remain the same.

This means:

``` text
Player position
    ↓
Arena shrinks
    ↓
Position is remapped/clamped
    ↓
Laser direction remains unchanged
```

The server should perform the authoritative transformation.

------------------------------------------------------------------------

# 24. Eliminated Players

When a player is eliminated:

-   Mark them as eliminated.
-   Remove them from the active-player list.
-   Do not allow them to participate in future placement phases.
-   They can remain as a spectator.
-   Their player marker should disappear from the active arena.

Recommended spectator UI:

``` text
You were eliminated.

Watching the game...

Round 4
3 players remaining
```

# 27. Important Edge Cases

Handle:

### Player disconnects during lobby

Remove them from the room.

### Player disconnects during placement

Mark them disconnected.

If the player reconnects within a short grace period, restore their
player session.

### Player disconnects during reveal

Do not change already-calculated results.

### Host disconnects

Transfer host control to another connected player.

### Player leaves after being eliminated

The game continues.

### All players ready

Immediately start reveal.

### Countdown reaches zero

Automatically resolve players who have not manually pressed Ready.

### Only one player remains

Immediately finish the game.

### Team becomes empty

The opposing team wins.

# 28. Server Authority

The server must be authoritative for:

-   Room creation
-   Room joining
-   Player IDs
-   Player names
-   Team assignment
-   Host
-   Game settings
-   Current round
-   Countdown
-   Player ready state
-   Player positions
-   Laser angles
-   Arena size
-   Collision detection
-   Eliminations
-   Winner
-   Game phase

Never trust client-side messages such as:

``` text
"I hit Player 4."
```

The client should only send:

``` text
"My position is X/Y."
"My laser angle is X."
"I'm ready."
```

The server decides everything else.

# 30. Security / Anti-Cheat

There are no accounts, so the game does not need traditional
authentication.

However, basic multiplayer validation is required.

The server should validate:

-   Player belongs to the room.
-   Player is alive.
-   Player is currently in the placement phase.
-   Position is within allowed bounds.
-   Laser angle is valid.
-   Player cannot modify another player.
-   Player cannot change placement after being locked.
-   Player cannot send fake elimination messages.
-   Player cannot start a game unless they are the host.

# 37. One-Server Deployment

The production server should run one Node.js process.

Conceptually:

``` ts
const server = createServer(expressApp)

const io = new Server(server)

const nextApp = next({
  dev,
  hostname,
  port
})

const handle = nextApp.getRequestHandler()

expressApp.all("*", (req, res) => {
  return handle(req, res)
})

server.listen(PORT)
```

The same server handles:

``` text
Next.js SSR
Express
Socket.IO
Game state
```

No second backend server should be required.

# 40. Critical Gameplay Rule

The most important concept is:

> **Players should make decisions without knowing where the other
> players are.**

The game should create a simultaneous prediction/strategy experience.

During placement:

``` text
Player A sees:
A + A's laser

Player B sees:
B + B's laser

Player C sees:
C + C's laser
```

Nobody knows the others' locations.

Then:

``` text
                 REVEAL
                    ↓

       A ────────────────>
                         B ●

   C ●
      \
       \
        \───────────────> A
```

Everyone sees the same locked state.

The server determines the eliminations.

# 41. Final AI Development Instruction

When implementing this project, do not simplify the multiplayer
architecture into a local single-player simulation.

Build the real multiplayer foundation from the beginning.

Do not use a database.

Do not add accounts.

Do not create a separate backend server.

Use one Node.js server that combines:

``` text
Next.js SSR
+
Express
+
Socket.IO
+
In-memory game rooms
```

Keep the game logic on the server.

Keep rendering and interaction on the client.

Make the server authoritative.

Use normalized coordinates.

Make the hidden-placement mechanic secure by not sending hidden player
information to clients.

Use simultaneous collision calculation.

Make arena shrinking synchronized across all clients.

Keep the architecture modular so future features such as sound,
power-ups, obstacles, different laser types, spectators, or additional
game modes can be added without rewriting the core multiplayer system.

The first implementation should prioritize a **working multiplayer game
loop** over visual polish:

``` text
Create Room
→ Join Room
→ Lobby
→ Start
→ Secret Placement
→ Ready
→ Reveal
→ Hit Detection
→ Elimination
→ Arena Shrink
→ Next Round
→ Winner
```
